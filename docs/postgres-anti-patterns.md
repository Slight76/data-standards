# PostgreSQL anti-patterns and preferred alternatives

Baseline: 1.0.0. Applies when: a solution designs tables, writes queries, or reviews EF Core output against PostgreSQL

Decision: [ADR-0001](../adr/0001-adopt-data-standards.md). Rules become binding when this baseline is adopted; examples explain the policy and do not establish business requirements.

This is a review checklist. Each entry names the mistake, why it hurts on PostgreSQL specifically, and the alternative the team uses. It complements [Logical and physical database design](design-standard.md), [Persistence, transactions, and query behavior](persistence-standard.md), and [Database naming conventions](naming-conventions.md); it does not repeat their rules.

## Schema anti-patterns

| Anti-pattern | Why it hurts | Use instead |
| --- | --- | --- |
| `timestamp` (without time zone) | Stores wall-clock text with no instant semantics; EF Core maps `DateTime` with `Kind=Unspecified` and comparisons drift across hosts and daylight-saving changes. | `timestamptz` for instants, `date` for calendar days (NAME-002). Store a separate IANA zone id when local scheduling matters. |
| `varchar(n)` chosen by guess | The limit is a business rule disguised as a type; changing it later rewrites the table in some versions and forces a migration for a trivia question. | `text`, plus a `CHECK (length(col) <= n)` constraint when a real limit exists. Performance is identical. |
| `serial` / `bigserial` | Creates an implicit sequence with its own ownership and grant quirks; not SQL-standard; copying a table loses the default. | `bigint GENERATED BY DEFAULT AS IDENTITY` (EF Core default for Npgsql) or `uuid` when rows are created in several places. |
| `uuid` primary key generated as random v4 on hot insert tables | Random keys scatter B-tree inserts and inflate the index. | Accept it for modest volumes; for high-insert tables use identity or time-ordered UUIDs (v7) and measure. |
| Universal soft delete (`is_deleted` on everything) | Breaks unique constraints (deleted rows still collide), leaks through every query that forgets the filter, defeats erasure requests, and grows forever. | Hard delete with FK `ON DELETE` chosen deliberately; archive tables or an `archived_at` column only where retention requires it; partial unique indexes `WHERE deleted_at IS NULL` if a soft delete is approved. |
| JSONB as the default column type | Hides the schema from constraints, indexes, migrations, and EF Core; queries become string-typed and unplannable. | Normalized columns for anything you filter, join, or validate. JSONB for genuinely free-form payloads (webhook bodies, user preferences), with a GIN index only when queried. |
| Missing index on foreign-key columns | PostgreSQL does not index FK columns automatically. Deleting or updating a parent row scans the child table; joins to the child are sequential scans. | `ix_<table>_<fk>` on every FK unless a review records why not (PGX-001). |
| Everything in `public` | Grants, migration history, and extensions collide; the module boundary disappears. | One schema per owning module (NAME-004). |
| `money` type | Locale-dependent formatting and rounding. | `numeric(p, s)` with explicit scale plus a currency column. |
| Float for quantities or amounts | Binary rounding errors accumulate. | `numeric`, or `integer` minor units. |
| Nullable columns "just in case" | Null has three-valued logic; every query grows `IS NOT NULL` guards. | `NOT NULL` with a default or a documented reason for null (DB-007). |

## Query anti-patterns

| Anti-pattern | Why it hurts | Use instead |
| --- | --- | --- |
| `SELECT *` or tracking full entities for reads | Pulls unused columns, defeats covering indexes, and tracks every row in the EF Core change tracker. | Project to a DTO (`Select(x => new ...)`) and use `AsNoTracking()` for reads (DATA-001). |
| N+1 queries | A loop that lazy-loads or queries per row multiplies round-trips; Fly.io hosts the app and database in the same region, but 500 round-trips are still 500 round-trips. | One query with an explicit `Include`, a projection, or a batched `WHERE id = ANY(@ids)`. Assert query counts in integration tests. |
| Unbounded `IN (...)` / `Contains` with thousands of values | Generates a huge statement, blows the plan cache, and hits parameter limits. | Pass an array parameter (`= ANY(@ids)`, which Npgsql does for `Contains`) and cap the list; above a few thousand use a temporary table or a join. |
| `OFFSET` pagination | Page 500 reads and discards 499 pages; results shift when rows are inserted. | Keyset pagination: `WHERE (created_at, id) < (@after_created_at, @after_id) ORDER BY created_at DESC, id DESC LIMIT @n`, backed by a matching index. |
| Unbounded result sets | One bad filter returns the whole table into memory. | Always `Take(n)` with a maximum enforced in the query port (DATA-001). |
| `LIKE '%term%'` on large tables | Cannot use a B-tree index. | `pg_trgm` GIN index for substring search, or full-text search, or a search index as a derived store (DB-008). |
| `COUNT(*)` for "does any exist" | Counts every matching row. | `EXISTS` / `AnyAsync()`. |
| Casting the indexed column (`WHERE lower(email) = @e`, `WHERE created_at::date = @d`) | Hides the index. | Store normalized values (`citext` or lower-cased column) or create an expression index that matches the query exactly; use range predicates for dates. |
| `ORDER BY random()` | Full sort of the table. | `TABLESAMPLE` or an indexed random key. |
| Reading then unconditionally updating | Lost updates under concurrency. | Concurrency token or conditional `UPDATE ... WHERE row_version = @v` (DATA-002). |

## Transaction and operational anti-patterns

| Anti-pattern | Why it hurts | Use instead |
| --- | --- | --- |
| Long-running transactions (HTTP call, user wait, or a whole import inside one transaction) | Holds locks and blocks vacuum; the dead-tuple backlog bloats tables and indexes for every other tenant. | Keep a transaction to one business operation; do external I/O outside it; batch imports in committed chunks with a resumable checkpoint (MIG-002). |
| Migrations that rewrite large tables during deploy (`ALTER COLUMN TYPE`, adding a column with a volatile default on old versions, `CREATE INDEX` without `CONCURRENTLY`) | Takes an `ACCESS EXCLUSIVE` lock for the duration; the app is down. | Expand/contract migrations, `CREATE INDEX CONCURRENTLY` outside a transaction, `NOT VALID` constraints followed by `VALIDATE`, and a lock-timeout set for the migration session (MIG-001). |
| Running migrations from application startup | Every instance races to migrate; a failed migration takes the app down with it. | A separate deployment step with a schema-owning identity (DB-004, MIG-001). |
| Retrying a single failed statement inside a transaction | PostgreSQL aborts the whole transaction on error; the retry fails with "current transaction is aborted". | Retry the entire unit of work idempotently (DATA-002). |
| Treating a replica as a backup | Replicas replay the `DROP TABLE` faithfully. | Scheduled logical/physical backups with restore drills (DR-001; see the [backup and restore runbook](backup-restore-runbook.md)). |
| Connection pool sized by hope | Each PostgreSQL connection is a process; Fly Postgres machines are small, and 100 idle connections cost memory that the buffer cache needs. | Size the Npgsql pool from measured concurrency, set `Command Timeout` and `Timeout`, and add PgBouncer only with evidence (DATA-003). |
| `EXPLAIN ANALYZE` on production writes | It executes the statement. | `EXPLAIN` only, or `EXPLAIN ANALYZE` inside a transaction you roll back on a non-production copy. |

## How to use this list

Run through the schema table when reviewing a migration and through the query table when reviewing a repository or query port. Cite the entry in the PR comment; propose the alternative, not just the objection. If the team deliberately accepts an anti-pattern (for example JSONB for a payload column), record the reason in the entity configuration comment so the next reviewer does not reopen it.

Sources: [PostgreSQL "Don't Do This" wiki](https://wiki.postgresql.org/wiki/Don%27t_Do_This), [Npgsql EF Core provider documentation](https://www.npgsql.org/efcore/), [Use The Index, Luke on keyset pagination](https://use-the-index-luke.com/no-offset). The thresholds and preferred alternatives are our policy.

## Rules and required evidence

| ID | Requirement | Verification |
| --- | --- | --- |
| PGX-001 | Every foreign-key column MUST have a supporting index, or a recorded review note explaining why the access pattern never needs it. | Schema query listing FK columns without an index returns only documented cases |
| PGX-002 | List endpoints and background readers MUST use keyset pagination and bounded page sizes; `OFFSET` pagination MUST NOT be used beyond the first few pages. | Query review and integration test with a page cursor |
| PGX-003 | Migrations MUST NOT take long `ACCESS EXCLUSIVE` locks on tables with production traffic; indexes MUST be created concurrently and constraints validated separately. | Migration SQL review and lock-timeout setting in the deployment step |

## Exceptions

Use the [exception record](https://github.com/Slight76/standards-marketplace/blob/main/templates/exception.md) for a departure. Record affected rules, scope, compensating controls, approval evidence, expiry, and migration path. Agents must not silently replace defaults.
